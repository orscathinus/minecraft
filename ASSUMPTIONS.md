# Cave Game Tech Test Recreation — Assumptions and Approximations

## 1. Purpose

The historical target does not document every implementation value needed to build a stable prototype. This file records conservative defaults for those missing details.

Every numbered item below is an **approximation**, not a claim about the original May 13, 2009 implementation. Approximation values may be tuned later when visual comparison or playtesting provides better evidence, but they must never override a requirement in [`SPEC.md`](SPEC.md).

## 2. Coordinate and storage approximations

### A-01 — Coordinate convention

**Approximation:** World coordinates are right-handed: +X east, +Y up, and +Z south. Block cells occupy half-open unit ranges such as `[x, x+1)`. The player's position is the center of the collider at its feet on X/Z and the collider's bottom on Y.

**Reason:** This convention is simple, conventional for voxel collision, and avoids ambiguity at block boundaries.

### A-02 — Chunk vertical structure

**Approximation:** A horizontal chunk stores one `16 × 64 × 16` block volume. There are no vertically stacked chunk sections.

**Reason:** The world is only 64 blocks high, so vertical subdivision adds complexity without helping this prototype.

### A-03 — Outside-world lookup

**Approximation:** Any block lookup outside X `0..255`, Y `0..63`, or Z `0..255` returns `AIR` to collision and rendering callers, while write attempts outside the world are rejected.

**Reason:** This naturally permits walking or falling off the finite map and supports the documented non-lethal void.

### A-04 — World seed

**Approximation:** Generation uses a signed 64-bit seed. The default seed is fixed in development and may be randomized once per application launch in release builds; no seed-selection user interface is added.

**Reason:** A seed makes generation reproducible for tests without adding a modern world-creation screen.

## 3. Terrain and cave approximations

### A-05 — Surface height field

**Approximation:** Terrain surface height is generated by deterministic two-dimensional fractal value noise with four octaves, persistence `0.5`, lacunarity `2.0`, and a broad base frequency near `1/96` blocks. The result is scaled and clamped to Y `57..63`.

**Reason:** This produces broad, restrained hills while ensuring grass-eligible terrain remains in the documented upper seven layers.

### A-06 — Base terrain fill

**Approximation:** For each X/Z column, all cells from Y `0` through the generated surface height begin as `ROCK`; cells above begin as `AIR`. Grass replacement and cave carving occur afterward.

**Reason:** This is the smallest deterministic terrain model compatible with the three permitted block states.

### A-07 — Cave algorithm

**Approximation:** Caves are carved by deterministic seeded random-walk tunnel paths. Each path moves through three-dimensional space with smoothly changing heading and uses a rounded radius between approximately `1.5` and `3.5` blocks. Paths start at or just below the surface, may connect to the surface, and are biased to explore downward without carving below Y `1`.

**Reason:** Tunnel walkers create recognizable early voxel caves and make it straightforward to guarantee occasional surface openings and deep passages.

### A-08 — Cave density

**Approximation:** Begin with approximately 32 tunnel paths across the entire `256 × 256` world, each lasting roughly 80 to 220 carving steps. Tune only enough to create substantial caves without hollowing most of the map.

**Reason:** The target needs visible caves, but not a modern dense cave network. Exact historical density is unspecified.

### A-09 — Lowest layer

**Approximation:** Y `0` is an uncarvable `ROCK` floor wherever it lies inside the world footprint. Cave carving may replace rock with air at Y `1` and above.

**Reason:** This is the clearest implementation of “toward the second-lowest stone layer.”

### A-10 — Grass conversion order

**Approximation:** Terrain and caves are generated first, sunlight visibility is computed second, and eligible exposed sunlit `ROCK` blocks in Y `57..63` are converted to `GRASS` last.

**Reason:** This prevents grass inside dark caves and permits grass around genuinely sunlit cave openings.

## 4. Player and movement approximations

### A-11 — Fixed simulation rate

**Approximation:** Player physics run at a fixed 60 updates per second, with rendering interpolated or independently refreshed.

**Reason:** A fixed step makes collision and movement tests deterministic while remaining responsive.

### A-12 — Collision shape

**Approximation:** The player uses an axis-aligned box `0.60` blocks wide, `0.60` blocks deep, and `1.62` blocks tall.

**Reason:** The height matches the documented approximation, while a 0.60-block width is conservative and familiar for narrow voxel passages.

### A-13 — Eye height

**Approximation:** The camera eye is `1.52` blocks above the player's feet.

**Reason:** This keeps the camera just below the top of the 1.62-block collider and avoids ceiling clipping.

### A-14 — Movement speed

**Approximation:** Ground movement speed is `4.3` blocks per second. There is no sprint multiplier, crouch speed, or diagonal speed advantage.

**Reason:** This is a restrained walking pace suitable for a small world and avoids importing later movement modes.

### A-15 — Acceleration and friction

**Approximation:** Ground acceleration reaches target speed in approximately `0.15` seconds. Ground friction stops an uncommanded player in approximately `0.12` seconds. Air control is 25% of ground acceleration.

**Reason:** These values feel direct without making movement perfectly instantaneous or adding complex momentum systems.

### A-16 — Gravity

**Approximation:** Downward acceleration is `20` blocks per second squared, with a terminal downward speed of `50` blocks per second.

**Reason:** The value produces clear, game-like falling and keeps collision steps manageable.

### A-17 — Jump impulse

**Approximation:** A grounded Space press sets vertical velocity to `7.5` blocks per second, yielding a jump apex of roughly 1.4 blocks under A-16 gravity.

**Reason:** This clears a one-block rise while remaining below a two-block jump.

### A-18 — Step handling

**Approximation:** There is no automatic step-up system. The player must jump to ascend a full block.

**Reason:** This is simpler and avoids assuming a later convenience mechanic.

### A-19 — Field of view

**Approximation:** The perspective camera uses a 70-degree vertical field of view, adjusted normally for aspect ratio.

**Reason:** The original FOV is unspecified; 70 degrees is conservative and avoids an exaggerated modern wide-angle appearance.

### A-20 — Mouse look

**Approximation:** Raw cursor delta rotates the camera by `0.15` degrees per pixel. Yaw is unrestricted; pitch is clamped to `-89` through `+89` degrees. The cursor is captured while the window is focused.

**Reason:** This is a minimal first-person mouse-look implementation that prevents camera inversion at the poles.

### A-21 — Initial facing direction

**Approximation:** On launch or respawn, the player retains current yaw and pitch. On first launch only, yaw faces toward negative Z and pitch is level.

**Reason:** The target specifies respawn position but not camera reset behavior; retaining orientation is less disruptive.

## 5. Respawn approximations

### A-22 — Valid random X/Z

**Approximation:** Respawn samples X and Z independently from block columns `1..254` and places the collider at the selected column center (`n + 0.5`). The one-block margin reduces immediate edge falls while remaining random within the world footprint.

**Reason:** “Valid” is unspecified. A small margin is conservative and does not create an invisible boundary.

### A-23 — Respawn obstruction check

**Approximation:** Because Y `74` is above the world, every in-bounds sampled X/Z is considered vertically unobstructed. No terrain-height or surface-safety search is performed.

**Reason:** The documented Y position is already ten blocks above the highest valid block layer.

### A-24 — Hold-R repeat rate

**Approximation:** Respawn occurs immediately when R becomes held, then repeats once every `0.10` seconds while R remains held.

**Reason:** This visibly satisfies repeated respawning without tying behavior to operating-system keyboard-repeat settings or triggering 60 randomizations per second.

### A-25 — Respawn state reset

**Approximation:** Respawn sets linear velocity to zero and grounded state to false, while preserving camera orientation.

**Reason:** Resetting velocity gives consistent falls from Y `74`; other state does not need to exist in this prototype.

## 6. Lighting and visual approximations

### A-26 — Binary face lighting

**Approximation:** Each visible solid face is marked `BRIGHT` when the adjacent air cell is directly skylit by the vertical sunlight scan; otherwise it is marked `DARK`. Brightness is constant across each face.

**Reason:** Per-face assignment preserves the required two-level look and allows cave mouths and exposed cliffs to react to skylight without smooth propagation.

### A-27 — Brightness multipliers

**Approximation:** Bright faces use a multiplier of `1.0`; dark faces use `0.28`. No directional face shading is added.

**Reason:** This creates an unmistakable bright/dark split while respecting the requirement that lighting have only two meaningful levels.

### A-28 — Texture resolution and filtering

**Approximation:** Original grass and rock placeholder textures are `16 × 16` RGBA images, sampled with nearest-neighbor filtering and no mipmaps in the first fidelity pass.

**Reason:** Low-resolution nearest-neighbor textures fit the historical visual target and avoid copyrighted assets.

### A-29 — Placeholder texture appearance

**Approximation:** Grass uses a simple project-created green pixel pattern and rock uses a simple project-created gray pixel pattern. Neither texture imitates or traces a Minecraft texture.

**Reason:** The project needs readable materials while remaining legally and artistically independent.

### A-30 — Projection clipping planes

**Approximation:** The camera near plane is `0.05` blocks and the far plane is `256` blocks.

**Reason:** These values support close voxel surfaces and the entire finite map without excessive depth-buffer loss.

### A-31 — Dark fog curve

**Approximation:** Dark-face fog begins at 12 blocks, reaches full black at 48 blocks, and uses a linear distance factor initially. Fog is calculated from camera-space distance.

**Reason:** This is intentionally heavy and makes cave interiors disappear rapidly, matching the documented effect.

### A-32 — Bright fog treatment

**Approximation:** Bright geometry blends toward sky color beginning at 96 blocks and reaches full sky color at 192 blocks.

**Reason:** The requirement singles out dark blocks for heavy black fog. A much later sky-colored fade prevents harsh distant clipping outdoors without competing with the black cave effect.

### A-33 — Clear and background color

**Approximation:** The framebuffer clears to sRGB `#7FCCFF`; no gradient sky dome is used.

**Reason:** A flat clear color is the smallest implementation of the exact required sky color.

### A-34 — Display defaults

**Approximation:** The first window is `1280 × 720`, resizable, windowed, and uses vertical synchronization. Fullscreen and graphics menus are not added.

**Reason:** These are development conveniences that do not change world behavior or add modern game systems.

## 7. Chunk, meshing, and render approximations

### A-35 — Proximity metric

**Approximation:** Chunk work is ordered by squared Euclidean distance in the horizontal chunk plane from the player's current chunk. Ties are broken by chunk Z and then chunk X for deterministic tests.

**Reason:** Squared distance avoids square roots and provides an unambiguous nearest-first order.

### A-36 — Work granularity

**Approximation:** At most one previously ungenerated or dirty chunk mesh is completed per rendered frame during ordinary play. Tests may execute the queue synchronously.

**Reason:** This makes proximity order visible and avoids a large startup stall while keeping scheduling simple.

### A-37 — Render distance

**Approximation:** The renderer draws chunks whose centers are within an 8-chunk horizontal radius of the player's chunk, clipped to the finite world grid.

**Reason:** Eight chunks is conservative for a `16 × 16` world and allows fog to hide the draw boundary in most views.

### A-38 — Chunk retention

**Approximation:** Generated block data and completed meshes remain cached for the session; distant chunks are not unloaded because the world contains only 256 chunks.

**Reason:** Session-long caching is simpler and bounded for this finite prototype.

### A-39 — Mesh format

**Approximation:** Each chunk produces one opaque triangle mesh with position, texture coordinate, and one binary-light attribute per vertex. Faces between solid blocks are omitted.

**Reason:** All permitted blocks are opaque, so material sorting, transparency, and multiple render passes are unnecessary.

### A-40 — Threading

**Approximation:** World generation and meshing begin single-threaded. Background workers may be added only if profiling shows a need and deterministic ordering remains observable and testable.

**Reason:** The world is small, and simple deterministic behavior is preferable to premature concurrency.

## 8. User-interface and lifecycle approximations

### A-41 — Startup

**Approximation:** Launching the application enters the world directly after initialization. There is no title screen, loading menu, options screen, or world-selection interface.

**Reason:** The target is a tech test, not a complete game.

### A-42 — Exit control

**Approximation:** Escape releases/captures the cursor on first press and closes the window when pressed while already released, or the native window close button exits immediately.

**Reason:** The historical exit behavior is unspecified, but a safe desktop exit path is necessary.

### A-43 — Debug information

**Approximation:** Development builds may show the seed, player coordinates, current chunk, frame rate, and chunk-queue state in the window title or console. Final presentation may disable this output.

**Reason:** Diagnostics help verify proximity ordering and world bounds without adding gameplay UI.

## 9. Revision policy

When an approximation is changed:

1. retain its approximation label;
2. document the reason for the change;
3. update tests or acceptance checks affected by it;
4. confirm that no required behavior or non-goal in `SPEC.md` has changed.
